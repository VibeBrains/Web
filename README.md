# VibeIDE — лендинг vibeide.ru

Продающая страница [VibeIDE](https://github.com/VibeBrains/VibeIDE) — открытого AI-редактора кода.
Цель страницы одна — **скачивания**: главный CTA ведёт прямо на установщик, всё остальное работает
на это решение.

Статика без единой внешней зависимости: ни CDN, ни подключаемых шрифтов, ни аналитики. Это и
быстрее, и честнее по отношению к продукту, который не отправляет телеметрию.

## Структура

```
site/            то, что уезжает на сервер
  index.html     разметка
  styles.css     стили, светлая и тёмная тема
  app.js         прогрессивное улучшение: тема, копирование команды, живые релизы
  assets/        логотип и иконка
scripts/
  setup-ssh.sh       разовый засев SSH-ключа (пароль вводит человек)
  deploy.sh          выкат по rsync
  refresh-links.mjs  подстановка актуальных ссылок на сборки в разметку
  lib-env.sh         загрузка настроек из .env
deploy/nginx/    конфиг веб-сервера, под которым сайт живёт
```

## Настройка

Адреса сервера в репозитории не хранятся — заполните их локально:

```bash
cp .env.example .env
$EDITOR .env
```

`.env` в `.gitignore`. Любое значение можно переопределить переменной окружения.

## Первый запуск

```bash
./scripts/setup-ssh.sh
```

Скрипт создаёт ключ, добавляет запись в `~/.ssh/config` и копирует публичный ключ на сервер —
**пароль на этом шаге вводит человек**, один раз. Скрипт идемпотентен: повторный запуск ничего
не ломает и не дублирует.

## Выкат

```bash
./scripts/deploy.sh --dry-run   # посмотреть, что изменится
./scripts/deploy.sh             # выкатить
```

`deploy.sh` обновляет ссылки на сборки, синхронизирует `site/` через `rsync --delete`
и проверяет, что сайт отвечает 200.

## Почему ссылки на скачивание генерируются

Релизы VibeIDE **поплатформенные**: исправление под одну ОС выпускается отдельным тегом, и тогда
`releases/latest` указывает на релиз, где сборки для другой платформы просто нет. Универсальная
ссылка вида `releases/latest/download/VibeIDESetup.exe` в такой момент отдаёт **404** — проверено
29.07.2026, когда latest был macOS-only.

Отсюда двухслойная схема:

1. `refresh-links.mjs` вписывает в разметку прямые URL последней сборки **под каждую платформу** —
   работает и без JavaScript;
2. `app.js` при загрузке обновляет их через GitHub API, если после выката вышел новый релиз.
   Недоступен API или упёрлись в rate limit — остаются ссылки из пункта 1.

## Веб-сервер

Конфиг лежит в [deploy/nginx/vibeide.conf](deploy/nginx/vibeide.conf): HTTP редиректит на HTTPS,
сертификат Let's Encrypt выпускается через webroot и продлевается системным таймером certbot.

`index.html` отдаётся с `Cache-Control: no-cache` — иначе после релиза посетитель с закэшированной
страницей ещё сутки видел бы ссылки на предыдущую сборку. Ассеты кэшируются на неделю.

Меняете конфиг на сервере — перенесите изменение сюда и закоммитьте, иначе настройка существует
в единственном экземпляре на машине.

## Правки контента

Тексты берут смысл из основного репозитория: блок сравнения — из его `README.md`, карточки
возможностей — из `docs/functional.md`. Меняется продукт → сначала обновляется `functional.md`,
потом лендинг, а не наоборот.

## Автовыкат

Пуш в `main`, затрагивающий `site/`, запускает [Deploy](.github/workflows/deploy.yml) — сайт
выкатывается сам. Тот же workflow можно запустить руками из вкладки Actions: ссылки на сборки
живут в разметке, поэтому после релиза VibeIDE выкат нужен даже без изменений в репозитории.

Ключ деплоя ограничен на стороне сервера forced command'ом в `authorized_keys`:

```
command="/usr/bin/rrsync -wo <docroot>",restrict ssh-ed25519 AAAA…
```

Им нельзя выполнить произвольную команду и нельзя выйти за пределы каталога сайта — проверено
попытками (`id` отбит, запись в домашний каталог отбита). Поэтому в workflow нет ни одного шага,
который что-то запускает на сервере: только `rsync`. Путь назначения там относительный (`:.`) —
корень задаёт forced command, абсолютный склеился бы сам с собой.

Секреты репозитория: `DEPLOY_SSH_KEY`, `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS`
(хост-ключ зафиксирован секретом, а не `ssh-keyscan` на лету — скан доверяет тому, кто ответил).

Локальный `./scripts/deploy.sh` никуда не делся и ходит по обычному ключу — он полезен, когда
нужно выкатить, не коммитя. На macOS системный `rsync` — это openrsync (протокол 29), и через
ограниченный CI-ключ он не работает; в Actions используется настоящий rsync 3.x.
